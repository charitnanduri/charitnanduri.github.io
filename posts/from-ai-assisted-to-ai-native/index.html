From AI-Assisted to AI-Native

Our vision, the tools we use, and how we build — an overview of what it means to build a codebase where AI agents are first-class builders, operators, and explainers.

Most teams use AI. Far fewer are built for it. This is the gap that matters — and an overview of how we close it: the vision, the tools, and the practices that make a codebase something AI can build, run, fix, scale, and explain.

The vision#

We are building toward the AI-Native Repository: a codebase deliberately shaped so AI agents are first-class builders, operators, and explainers of the system, not bolted-on helpers. In plain terms, a repo where:

  • AI builds it — new features, APIs, integrations, infrastructure, written by agents under a developer’s direction.
  • AI maintains and fixes it — agents read logs, find the root cause of a prod bug, and propose the fix.
  • AI scales it — the system is designed so growth is a setting you turn, and agents help operate it there.
  • AI documents and explains it — anyone can ask the repo “where does this happen,” “why is it built this way,” “what breaks if I change it,” and get a grounded answer.
  • AI works with AI — the system exposes tools and APIs that agents can use, so automation can build on top of it at any level of complexity.
  • And it helps every engineer — to ship a feature, fix an incident, or make a call — by being legible and operable enough that the agent is genuinely useful.

The discipline of building and running such a repo is AI-Native Engineering. The point isn’t to use AI more. It’s to build a system AI is good at, because that system compounds: every improvement to it pays off on every future task, for every developer and every agent.

Our living example is Agent OS (A3) — eSentire’s platform for building multi-agent workflows from YAML. It’s both a thing we build with AI and a thing built for AI to operate, so it shows the whole idea at once.

The keeper. Using AI is a habit you can start this afternoon. Being AI-native is a property you build into the repo, the lifecycle, and the team — and it’s the one that compounds.

The shift: from assisted to native#

AI-assisted (most teams)AI-native (the goal)
Who drivesHuman types, AI suggestsHuman directs, agent executes
Unit of workA keystroke savedA task completed
You optimizePrompts and keyboard habitsThe system — context, tools, tests, docs
The ceilingYour typing speedYour judgment and verification

For most of software’s history the slow part was producing code. That’s going to the machine. When drafting is cheap, the real work moves to specifying what you want and verifying you got it. Your posture changes with it — the Director model: you specify, direct, verify, and decide; the agent does the typing. The unit of work is the developer + agent pair, not the developer alone. Prompt tricks don’t compound. Systems do.

Why build for it on purpose? The evidence points one way:

FindingWhat it means for us
DORA: AI is an amplifierIt multiplies what’s already there. A clean, documented, tested system gets faster; a mess gets worse, faster.
METR: experienced devs ran ~19% slower with AI on code they knew well — while believing they were fasterYou can’t trust the feeling of speed. Measure outcomes, not vibes.
MIT: ~95% of enterprise AI pilots returned nothing measurable — blamed on integration, not the modelsUsing AI is not the same as getting value. The system around the model is the variable.

Same technology, opposite outcomes — the difference is the context it ran in. The lever is legibility plus discipline, not model horsepower.

Where you are: the maturity ladder#

A six-level map of how much of the work your repo can let an agent safely carry:

L0L1L2L3L4L5
Ad hocAssistedSupervisedLegibleOperableOperated
chatbots on the sideautocomplete in the editorwhole tasks, watched, half tossedagent gets correct context cheaplyscoped tools + evals + gatesagents run parts of the lifecycle

L3 is the turning point — below it, people use AI; above it, the system is built for AI. Score yourself: say yes to a level only if you can also say yes to every level below it.

  1. (→L1) Do developers use AI day to day?
  2. (→L2) Do you hand over whole tasks and review the result?
  3. (→L3) Can a fresh agent finish a real task from the repo alone — no tribal knowledge?
  4. (→L4) Does the repo expose scoped tools, with specs/evals and review gates?
  5. (→L5) Do agents run parts of the lifecycle in guardrails, safely and observably?

You move up by paying down legibility debt — the docs, conventions, and examples that live only in people’s heads — not by buying tools. A sharper tool moves you zero levels on a repo an agent can’t read. Most teams land at L1–L2 and are surprised, because it doesn’t match how advanced they feel.

The tools we use#

Underneath the brand names, every coding agent runs the same loop: read context → propose an action → run a tool → read the result → repeat, with you directing and verifying at the edges. Learn the loop and you can pick up any tool quickly. Pick by how it fits the work, not by the logo.

CategoryExamplesWhat it’s for
Inline assistantGitHub Copilot, editor chatFast completions and questions while you drive the keyboard
Plan-execute agentClaude Code, OpenAI Codex, Amazon KiroHand over a whole task in an existing repo; it plans, edits, runs tests, iterates
Agentic IDECursor, Windsurf, Google AntigravityThe agent plus a visual editor in one place
Spec toolkitsGitHub Spec Kit, KiroTurn a ticket into a spec the agent can execute step by step
Connective standardMCP (Model Context Protocol)One open protocol so any agent can use any tool or data source
Infrastructure via MCPPostgres/RDS, Redis, S3, GitHub serversLet an agent read a real schema, run a safe query, or check a cache before it writes code
Our platformAgent OS (A3)Build, run, and operate multi-agent workflows from YAML

A common, effective setup is a daily IDE plus a deep terminal agent for heavier work. The strongest pattern is running several agents in parallel on independent slices of work, with the developer reviewing and integrating. The habit that pays most, on any tool, is plan mode: let the agent draft an approach and approve it before it touches code, so you catch wrong assumptions while they’re a sentence, not a diff.

MCP is worth calling out because it’s the connective tissue. It’s an open standard — “USB-C for AI tools” — so a tool you expose once works with any agent that speaks it. You use an existing MCP server for mainstream systems (GitHub, Slack, a database) and build your own for proprietary or messy internal APIs, consolidating them into a few clean, agent-shaped tools.

And across the rest of your stack. The AI-native moves don’t care which language or cloud you use — they care about the category. Swap in your own:

The constant under every row: a typed contract, a way to run and verify locally, structured output an agent can read, and least-privilege access. Give an agent those and it works your stack, whatever the logos say.

How Agent OS works#

Agent OS is our reference for “built for AI.” The mechanics are worth knowing because they show the patterns in this overview made real:

  • Workflows are YAML, not code. You declare an agent, or a supervisor coordinating several agents, in a YAML spec. The platform (built on LangGraph and AWS Bedrock) runs it. Hard problems are handled by decomposing into agents under a supervisor — that’s how it scales to any complexity.
  • Memory is built in. Multi-turn sessions keep conversation history with automatic summarization, stored locally for development or in a managed database in production.
  • It manages cost. Prompt caching keeps the stable parts of a prompt cheap to re-send, and each agent can name its own model — a cheap, fast model for mechanical work and an expensive one only where judgment lives.
  • It scales by configuration. The same system runs locally and synchronously for development, then switches to a distributed, queue-backed mode for production by changing a flag.
  • It has a safety floor. Security guidance is injected into every agent by default, with pattern checks for sensitive data.
  • It ships as config. A new workflow is YAML, reviewed and merged through a content repository, then picked up automatically — the PR review is the gate.
  • It operates over an API and an MCP server. An agent can list, validate, run, and read the logs of workflows itself — so the platform can be driven by AI, not just by people.

How we build#

Lay the foundation#

Before building on a repo, make it legible — cheap for an agent (or a new teammate) to get correct context. The test: can a cold agent finish a real task from the repo alone? You earn that with one-command setup, test, and lint so the agent can run and check its own work; an instruction file at the root (AGENTS.md / CLAUDE.md, commands first); named seams an agent can navigate by; and runnable examples to copy. Then manage context and memory: treat the window as a budget, because quality drops as you overfill it and the model re-sends the whole history every turn. Keep it lean with prompt caching, scoped tools, model-tier routing, and trimming (/compact, /clear). Set a guardrail floor: allow/ask/deny permissions, separate “propose” from “apply” for anything irreversible, and watch for prompt injection (danger needs private data + untrusted input + a way out, all at once — break any one leg).

Build features#

The output is only as good as the spec, so resolve ambiguity first and right-size it to the task. Then work the agentic loop — direct, let the agent act, verify, correct — in small verifiable slices, using sub-agents and git worktrees to run independent work in parallel (about 4–8 before your review saturates, which is the real limit). Two review flows run together: AI reviews code fast, and humans review AI — the verification gap is the central new risk, so read diffs critically. Tests are autonomy headroom (the more of the contract they pin down, the more an agent can safely change), and evals are tests for judgment-shaped behavior, run as a gate in CI so a build that drifts can’t merge. Before it writes an endpoint, the agent connects to the real database (a read-only Postgres/RDS MCP) and reads the actual schema and a few rows, so it codes against reality, not a guess — same for a cache like Redis — and it tests the change against a real, throwaway database, not mocks that encode the same wrong assumptions. Every integration gets the same resilient shape — timeout, retry, circuit breaker, and an idempotency key so a retry can’t fire twice — and docs are co-located and maintained in the same change as the code.

Run it and scale it#

A tight local loop lets an agent run the real thing and fix itself. In CI, deploy-and-verify: a preview environment plus smoke checks and evals, gated on the checks. Treat the deploy config as code applied behind a gate — generate freely, apply deliberately, always with a human reading the diff. This move is the same on Kubernetes, Lambda, ECS, or a plain VM; only the tool changes. The aim for scale is that growth is a config flip, not a rewrite (synchronous → distributed, local store → managed database). Cost at scale is token spend, controlled by caching, model routing, and a budget per run. And the system should be agent-debuggable: structured logs, correlation IDs across services, and dashboards an agent can read, so the prod-bug loop becomes alert → agent triage → root cause → proposed fix → human gate → ship → verify.

Build for AI as a user#

Make the system something an agent can operate, not just read, by giving it an agent-operable surface: tools that look like a good API for a sharp new hire — small, well-named, honest errors, typed; consolidated around real workflows; search/filter rather than list-everything; read access cheap and act access gated. Expose them over MCP so any agent can use them. The payoff is a repo that explains itself: an agent answers questions and onboards people from the instruction file, the docs, the operable surface, and the logs — and, as a next step, lets someone describe what they want in plain language and drafts a validated change for review. An unexplainable repo is an unmaintainable one.

The engineer’s job#

AI does more of the typing and raises the bar on judgment. Fundamentals matter more, not less — you can’t verify what you don’t understand, and only real knowledge catches confident, plausible-but-wrong output. The skills worth building are writing specs, curating context, designing tools and MCP, evaluating and verifying, and orchestrating agents. What stays your job is judgment, taste, decisions, and owning the integration — delegating without verifying erodes your skill, while delegating with rigorous verification compounds it. Adopting it on a team is a trust problem before a tooling one: make it safe to show the ugly first draft, measure outcomes (cycle time, escaped defects) not vanity metrics, and do a little governance early.

How a change gets made, end to end#

To make the pattern concrete, here is a normal feature — add a tool that looks up a ticket — from request to running in production:

  1. Spec. Half a page: the goal, what must not change, the existing pattern to follow, and what “done” means (it returns the ticket, or a clean not-found).
  2. Plan. The agent drafts an approach in plan mode; you approve it before any code is written.
  3. Build in slices. First the agent reads the real schema and the relevant cache keys — read-only, over MCP — so it codes against reality. Then: happy path, errors and timeouts, wire it into a workflow, reading the diff after each slice. A sub-agent drafts the tests in parallel, run against a real throwaway database.
  4. Verify. Tests pass; a deterministic eval proves the not-found case; the agent validates the change against the platform.
  5. Ship. It goes up as a PR — code plus config. CI runs it in a preview environment and the evals gate the merge. A human reads the diff and approves.
  6. Observe. It emits a structured log line and a metric; you watch it behave in production, and an agent can read those logs if it misbehaves.
  7. Explain. Months later, an agent answers “where does ticket lookup happen, and why” from the repo alone — no original author needed.

The method is the same for a bug fix or an architecture call: specify, direct, verify, decide. Only the stakes and the tempo change.

The eight invariants — what lasts#

These hold no matter which model or tool wins, and each gets more true as AI improves:

  1. Context is finite and must be curated. 2. The model has no memory. 3. You can’t verify what you don’t understand. 4. AI amplifies the system it lands in. 5. Intent outlives code. 6. Tools converge on a shape, not a brand. 7. Trust is earned by verification, not granted by hype. 8. As capability rises, judgment becomes the bottleneck.

First moves this week#

  • Make setup, test, and lint each one command, then put those three lines at the top of a CLAUDE.md / AGENTS.md. (The biggest single win.)
  • Use plan mode for your next real task; approve the plan before any code.
  • Write down what the agent keeps getting wrong — that’s your legibility backlog.
  • Add one eval or test gate to something an agent touches.
  • Separate propose from apply for one risky action.
  • Measure one outcome, not a vanity metric.

The non-negotiables#

  • The verification gap is yours. As the model writes more, your ability to check is the ceiling. Read diffs critically; resource review like real work.
  • Fundamentals matter more, not less. Only real understanding catches confident, plausible-but-wrong output.
  • Guardrails make autonomy safe. Least-privilege tools, a human gate on irreversible actions, and an eye on prompt injection.

In one line. Make your system worth amplifying — build the repo, the lifecycle, and the habits so an agent can do the work and you can trust the result, then point the best model you have at it and keep your hand on the wheel.
